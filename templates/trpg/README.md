# 初見卓で試すワンショットTRPG

「こういう卓で遊びたい」と一言渡すと、GMが読めるシナリオと、初見のPCが実際に何に驚き、何を選んだかの記録ができる。ハッカソン当日は、参加者が最後の場面だけ実際に遊び、模擬卓と違う結末を作れる。

## 動かす

Node.js 24以降とログイン済みの Codex CLI があれば、依存パッケージのインストールは不要。リポジトリのルートで実行する。

```sh
just trpg                    # 質問に答えて新しいシナリオを作り、自動試遊する
just trpg '月面図書館の閉館前夜に貸出票の謎を解き、最後に誰に何を貸すか自分たちで決めたい'
cp templates/trpg/table.json my-table.json
just trpg '' my-table.json   # 作者が配役や約束を決めた卓
just trpg '終電の忘れ物をめぐる交渉劇' '' 60   # 60分で人間が遊べる設定を生成
```

端末で `just trpg` を実行すると、ジャンル、卓でやりたいこと、舞台や場面、遊ぶ時間の順に尋ねる。ジャンルはミステリ、脱出ゲーム、DnD風の冒険、クトゥルフ的なホラー、SCP的ホラー、ダークファンタジーから選べる。`2、5、役所コメディ` のように番号と自分の言葉を混ぜてもよい。舞台には「夜勤中、エレベーターが存在しない階で止まる」など、思い浮かんだ場面を一行で書ける。時間は30分か60分。ジャンル以外は Enter でおまかせにできる。

最後の回答を受け取ると、回答と生成に使うお題を `runs/trpg-*/interview.json` に保存し、シナリオ生成と試遊を始める。お題か設定ファイルを直接渡すと質問を省く。自動実行など標準入力が端末でない場合、引数なしなら同梱の映画館のお題を使う。保存した4行の回答を使うには `just trpg --interview < answers.txt` を実行する。

設定ファイルを指定しないときは、作者の1回の呼び出しで約束、配役、揺らぎカード、ハンドアウト、シナリオ本文を同時に生成する。設定ファイルも渡す場合は、その約束と配役を優先し、一言は `wish` の上書きに使う。`TRPG_AGENT` が作者・GM・PC、`TRPG_JUDGE_AGENT` が編集者のCLI（codex / claude / pi）で、未指定なら両方Codex。Pi を mise 管理しているローカル環境の例は `MISE_NODE_VERSION=24.12.0 TRPG_AGENT=pi TRPG_JUDGE_AGENT=codex just trpg`。別リポジトリに持ち出す場合は `trpg/` と `factory/agent.mts` の相対配置を保ち、`node trpg/run.mts` で動かせる。モデルを使わない検証は `node --test templates/trpg/*.test.mts`。

## 人間がPCを1席担当する

```sh
just trpg-play                              # 質問に答えて卓を作り、席1で遊ぶ
just trpg-play 2 '' templates/trpg/table-dungeon.json
TRPG_HUMAN_SEAT=2 just trpg-replay runs/trpg-XXXX/draft-1 1
TRPG_HUMAN_SEAT=2 just trpg-resume runs/trpg-XXXX/draft-1 1
```

席番号は配役順で1から始まる。人間の卓は1稿だけ遊び、ほかのPC・NPC・GMは通常のモデルが担当する。端末には自席の秘密の手札、公開状態、卓の新しい発言が届く。入力欄のすぐ上に、今の場面や相手の提案が短く出る。移動を選んだ後には、選んだ行動を見ながら台詞を入力する。発言の全文は `/log`、自分の手札は `/hand`、公開ルールは `/rules` で読み返せる。補助ルールがある卓では行動の番号も選ぶ。最後の応答が回ってきたら相手の案に答え、結末を読んで自分の感想を記入する。人間の席は行動だけを宣言し、遊び終わってから感想を伝える。事前予想を記録するのはモデルの席だけ。

人間の行動と感想には `controller: "human"` が付き、担当した席は `models.json` の `humanSeat` に残る。`/quit` で試遊を中断できる。再開位置は既に保存されたGM裁定直前のチェックポイント。再開時も担当したい席を指定する。人間席が未指定なら全席自動で進む。

[HumanSeat](human.mts) が試遊エンジンとUIの境界になる。GUIを追加するときは、`observe` で公開状態を描画し、`act`、`reply`、`survey` を入力フォームにつなぐ。画面には卓全体の内部状態を渡さず、その席が読める情報に絞った `SeatView` を渡す。

## 作者が決めること

| 設定 | 書くもの | 映画館の例 |
|---|---|---|
| `minutes` | 人間が卓で遊ぶ目安。30か60。コマンドの第3引数で上書きできる | 30分は1か所で2場面、60分は別の現場を含む4場面 |
| `promise` | どんな結末でも守る体験 | 誰の記憶をどう残すかはPCが決める |
| `openQuestion` | 人間に答えを預ける問い | エンドロールの最後の一行に何を書くか |
| `players` | 異なる楽しみ方をする2〜3人の名前と望み | 仕掛けを試す映写係、持ち主の話を聞く配達人 |
| `complications` | 途中で揺らしてよい条件 | 閉館が早まる。手がかりは残り、選ぶ代償が変わる |
| `lens`（任意） | 自分の作風に固有の問い | 「上映しなかった人の記憶も尊重されたか」 |

人間が工夫する一番小さい単位はカード1枚。「鍵が消え、調査が無効になる」を「鍵はあるが、開けると持ち主に知られる」に変えるだけで、プレイヤーが考えることが変わる。世界の秘密、NPCの事情、分岐の候補は書いておき、決断と最後の台詞は卓に預ける。

PCやNPCには、卓の約束の範囲で、えこひいきや見栄も演じさせる。たとえば映写係なら「誰の映画にも同じ時間を」と提案することも、「父のフィルムを一分だけ先に流してくれたら、残りの編集は君に任せる」と持ちかけることもできる。後者を配達人が断り、代わりに一本だけ無音上映を提案したなら、その応酬と上映結果が創発を判定する材料になる。

## 設計資料を使ってGMの手引きを作る

作者には、選んだ資料の要点を日本語で渡す。生成した導入・卓の約束・時間配分・公開ルールをもとに、各資料を「この場面に来たら、GMが何を示し、どこからPCに委ねるか」という指針に書き換える。たとえば水没する塔なら、圧潮栓を使う前に何を伝え、誰が使うかをどの席に問うか、という形になる。

| 卓設定の資料ID | 出典と設計に使う観点 |
|---|---|
| `situations` | PCが想定外の手を選んでも反応できる状況を準備する。[Justin Alexander, Don’t Prep Plots](https://thealexandrian.net/wordpress/4147/roleplaying-games/dont-prep-plots) |
| `clues` | 必須の推理に至る手がかりを複数の経路に置く。[Justin Alexander, Three Clue Rule](https://thealexandrian.net/wordpress/1118/roleplaying-games/three-clue-rule) |
| `judgment` | 方法を選ぶPCと、その危険・効果・帰結を決めるGMの役割分担。[Blades in the Dark, The Core System](https://bladesinthedark.com/core-system) |
| `mda` | ルールから卓で生じる振る舞いと、プレイヤーが味わう体験の関係。[Hunickeほか, MDA](https://users.cs.northwestern.edu/~hunicke/MDA.pdf) |

既定は全4件。卓設定に `"designSources": ["situations", "mda"]` と書けば2件に絞れる。空配列は参照とガイドライン生成を無効にする。資料を増やすには[資料カタログ](design-sources.json)にID・著者・題名・原典URL・要点を追加する。原典の取得は試遊中には発生しない。

人間のGMは各稿の `scenario.md` の「GMの進行ガイドライン」から、適用する指針と原典を読める。モデルのGMには各手番で指針だけを渡す。PC・NPCへの配布や、ガイド生成時の秘密のハンドアウト参照は行わない。ガイドは各稿の `scenario.json` に保存し、再試遊・分岐では同じ文面を使う。この機能より前の保存稿は元の進行のまま再生できる。

## 体力や道具を賭ける卓

```sh
just trpg '' templates/trpg/table-dungeon.json
TRPG_MECHANICS=hp,items,dungeon just trpg '大潮の前に沈んだ灯台から一曲だけ持ち帰りたい'
```

卓設定の `mechanics` に使いたいものだけを書く。省略または `[]` が通常の会話卓。新規卓では `TRPG_MECHANICS` でも指定できる。作者は本文と同時に、突破する障害と、有効なルールの数値・名前を生成する。

| 設定 | 手番で迫られる選択 |
|---|---|
| `hp` | 指定量のHPを払って障害を突破するか、温存するか。HPは席別で、0になるとシナリオ固有の負傷を負う。会話や援護は続けられる。 |
| `items` | 共有品を突破に使うか、その場で本来の用途に使うか、次の人に残すか。どちらの使用も1手・1回分。残数0では使えない。 |
| `dungeon` | 順路を1手番で1区間歩くか、その場で行動するか。HPか道具も有効なら、代償を払って入口と目的地を結ぶ近道が通れる。PCは別々に移動できる。 |

地図は短い卓で3地点、長い卓で4地点。順路と近道の形を固定し、地点名と障害はシナリオごとに作る。地図を使わない卓では、突破の結果をGMがその場の物語に反映する。最終案への応答では追加の資源を消費しない。

各稿の `scenario.md` に人間用の公開ルール、`session.json` の各PC行動に選んだ手と結果、`mechanics.json` に初期設定と最終状態が残る。再試遊は同じ設定で最初から始まり、チェックポイント再開はそれまでの手を適用して当時の残量と位置を復元する。

道具のある卓では、編集者が公開ログの使用宣言・ルール結果・GM描写と残数を照合する。矛盾があれば `assessment.json` の `stockConflict` に場面IDを残し、改稿対象にする。

## 初見の人と30分卓を試す

同じシナリオを用意し、席と操作だけ案内する。開始から結末までの実時間、入力前に長く迷った場面、全文を見直した場面を観察者が控える。終了後に「どこで迷った？」「何を諦めた？」「相手の一言で変えた手はあった？」と聞き、答えを行動ログと並べる。作戦を考える時間と、選べる手が分からなかった時間を区別できる。

## 試遊と改稿

普段は `just trpg '遊びたい卓'` から始める。初稿は新規生成し、個別の失敗から得た教訓は、全ジャンル共通の次の問いで検証する。

| 指標 | 試遊ログで確認すること |
|---|---|
| clarity | 決断前に選択肢・代償・別案の余地が伝わったか。人間席なら画面の短文でも分かるか。 |
| feasibility | 残り時間や手段から見て、約束された選択を実行できたか。 |
| resolutionQuality | 選んだ行動が具体的な帰結につながったか。人物が譲った理由を卓で説明できるか。 |

編集者は各指標に合否・根拠の発言ID・理由を返す。未達があれば、同じ配役・設定で根拠を作者に返して改稿し、もう一度最初から試遊する。存在しない根拠は `CHECK_ASSESSMENT` として確認に回す。GMの手引き作成・試遊・監査には別途モデルを呼ぶ。各稿の成績は実行先の `quality.json` に蓄積する。

`just trpg-quality` は現行指標でレビューを完了した新規自動卓の件数、初稿合格数、最終稿合格数、初稿の指標別失敗件数を表示する。設定済みの卓・保存稿の再試遊・人間の試遊はこの集計から除く。同じ依頼を複数回試せば各実行を1件として数える。

1. 作者が時間配分に合わせて各場面の場所・小道具・切り上げ方を決める。各PCには別々の手がかりと秘密の勝利条件を配り、NPCには価値判断の偏りと譲歩の条件を与える。NPC役が公開の場で話し、PCは順に自分の一手を選ぶ。先手は場面ごとに交替する。PCに渡るのは自分のハンドアウト、自分の過去の予想、卓で公開された発言と行動。別の席の非公開メモやモデルの会話履歴は渡さない。
2. GMが各行動の帰結を語る。カードは最初の場面の末尾で開示する。最後の一手の前には、代償の違う案を含む問いを独立した公開項目 `D1` などに記録する。PCは第三案や保留も選べる。最終案が出そろったら、先に発言した席には各1回の応答（R）がある。相手の対案を初めて聞いた直後に卓が終わるのを防ぐ。最終場面のGMはPCが実際に選んだ行動を受けて結末を描く。PCが行動を決め、GMが世界の反応を担う役割分担は [Blades in the Dark の Core System](https://bladesinthedark.com/core-system) も参考になる。
3. 各PCが別々に「もう一度遊びたいか」「何を予想し、どこで外れたか」「なぜ結末に納得したか」「どの行動が効いたか」を答える。編集者は公開ログと感想を読み、約束・意外性の回収・選択の影響を照合する。
4. 編集者は「あるPCの提案を別のPCがどう作り替え、それが世界にどう効いたか」を `interaction` に記す。提案、応答、帰結の3件が公開ログに存在し、時系列と発言者が合うかをコードで検査する。単なる追従は創発に数えない。創発が観測できなかった場合とGMの矛盾が見つかった場合は改稿する。
5. 講評の場面IDと原文引用をコードで照合する。引用に根拠があり改稿が必要なら、1点を直して同じ配役・同じカードで再試遊する。合格は `READY_FOR_HUMAN`、改稿上限は `NEEDS_EDIT`、引用・創発の根拠・GMの整合性を判定できない場合は `CHECK_ASSESSMENT`。後二者の終了コードは1。人間の満足度は、人間が実際に遊んで初めて分かる。

`handouts/pc-1.json` などは各席に個別に渡す。各稿の `scenario.md` が配布用のGM冊子、`session.json` が卓に見えた出来事、`predictions.json` と `survey.json` が予想と感想、`assessment.json` が講評。**意外だったかは事前予想で、期待を裏切ったかは作者の約束と行動の帰結で**確かめる。同じ人でも前者は「はい」、後者は「いいえ」になり得る。採点者の平均点に合わせて作風を均す必要はない。[映画館での実測例](example.md)

## 同じシナリオを別の条件で試す

```sh
just trpg-replay runs/trpg-XXXX/draft-1 0
```

保存した稿と配役を再利用し、1卓だけ試遊する。ハンドアウトと場面設定が保存済みならそれも再利用する。旧形式の稿では不足分を1回生成し、新しい実行先に保存する。`seed=0` は揺らぎなし、1は1枚目、2は2枚目で、枚数を超えると先頭に戻る。seed が固定するのはカードで、モデルの台詞は毎回変わる。比較するなら同じ稿で「誰が最後に選んだか」を両卓のログから読む。

既定の30分・2人卓は1稿18呼び出し（作者1、ガイドライン生成1、NPC2、PC4、最終案への応答1、GM2、感想2、編集者1、整合性判定4）。整合性判定は導入・各場面のGM描写・最後の問いが対象。`maxRevisions: 0` で1稿だけ試せる。

## 同じ一手を別のDMが裁定したら

各場面でNPCと全PCが発言し終えた直後、GMを呼ぶ前に `draft-1/checkpoints/before-gm-N.json` ができる。ここには公開ログと席別の非公開の予想が入る。シナリオとハンドアウトは同じ稿の `scenario.json`、卓の条件は親ディレクトリの `table.json` にある。保存・移動するときは実行ディレクトリごと持ち運ぶ。

```sh
just trpg '' '' 30
# 第2場面のGM裁定、以降の試遊・感想・監査を新しい実行先でやり直す
just trpg-resume runs/trpg-XXXX/draft-1 2 templates/trpg/gm-limited.json
# 情報の与え方を保ち、GM役だけ別のCLIに交替
TRPG_GM_AGENT=claude just trpg-resume runs/trpg-XXXX/draft-1 2
```

[GMに渡す設定の見本](gm-limited.json)では、GMに真相・手がかり・NPCの人物像を渡す。作者の想定ルート・結末・各PCの勝利条件は伏せる。設定を初回から使う場合は `just trpg '' '' 30 templates/trpg/gm-limited.json`。分岐の設定ファイルを省くと親の設定を引き継ぐ。

| 設定 | GMにどう届くか |
|---|---|
| `metadata` / `gm.metadataKeys` | 実験名や対象者を文字列で記録する。指定したキーだけがGMに届く。 |
| `gm.sections` | `secret`, `clues`, `routes`, `ending`, `npc`, `handouts`, `beats` から選ぶ。空配列も可。題名・導入・公開済みの情報・依頼・時間配分は利用できる。 |
| `gm.history` | `all` は公開ログ全体、`scene` は直前のGM描写から現在のPC行動まで。 |
| `gm.notes` | 今回の裁定への追加指示。PC・NPC・編集者の入力には含めない。 |
| `TRPG_GM_AGENT` / `TRPG_GM_MODEL` | GMのCLIとモデルを指定する。役ごとの選択と分岐元は `models.json` に残る。 |

ルートの `calls.jsonl` はその実行でCLIに渡したプロンプトと返答、失敗を呼び出しIDで結び、`context.json` は適用済みの設定を保存する。GMへの入力だけを見るには次を使う。これらのログとチェックポイントにはGMの秘密やPCの非公開情報が含まれる。プレイヤーに渡すファイルはその席のハンドアウトと公開ログ。

```sh
jq -r 'select(.role == "gm" and .phase == "request") | .prompt' runs/trpg-XXXX/calls.jsonl
```

分岐では1稿を固定する。指定場面の裁定前の公開ログ・ハンドアウト・予想を継承し、その後の選択・結末・監査結果を新規に記録する。先のGM呼び出しが失敗していても、直前の保存点から再開できる。チェックポイント導入前の稿でも、ハンドアウト・対象場面の完了ログ・予想がそろっていればそこから復元する。分岐元の種類は `models.json` の `branch.origin` で確認できる。分岐前のCLIプロンプトまでさかのぼるときは、分岐元の実行ディレクトリも保管する。

## Jev でGMの矛盾を調べる

`TRPG_CONTINUITY_BACKEND=jev` を指定すると、各GM発言の時点での公開ログとGMの真相を TypeSafe の System One API に送る。質問は Choice 型。選択肢は「両立する」「情報不足」と、それまでにGMが確定した描写や真相のID。NPCが嘘をついたこと、時間が経って扉が開いたことは、それだけではGMの矛盾にならない。[TypeSafe 公式の Choice 仕様](https://docs.typesafe.ai/primitives/choice)

```sh
# TYPESAFE_API_KEY を設定した環境で
TRPG_CONTINUITY_BACKEND=jev just trpg '' '' 30
# 保存済みの同じログを監査。シナリオ生成・試遊の費用はかからない
TRPG_CONTINUITY_BACKEND=jev just trpg-audit templates/trpg/examples/moon/draft-1
```

`trpg-audit` は監査結果を標準出力に書き、全件が両立するなら終了コード0、矛盾や情報不足があれば1を返す。

各稿の `continuity.json` には判定対象の原文、矛盾相手に選ばれた原文、Jevが返したモデル名・選択肢ごとの確率・confidenceを保存する。既定は `cli` で、編集者用CLIが同じ選択肢を判定する。Jevを選択したときのAPIエラーは実行エラーとして記録する。モデルを固定する場合は `TRPG_JEV_MODEL` を指定する。

## ハッカソンでの使い分け

TRPGのほか、**脱出ゲームのヒント設計**には「謎を作る → 正解を伏せて初心者役が解く → 行き詰まった一手だけ直す」が合う。作者は「何に気づくと嬉しいか」を決める。**音声まち歩き**なら「案内を書く → 地元の人役と初訪問者役が別々に道を選ぶ → 迷った場所を比べる」が合う。現地でしか分からない音や足取りは、人間の取材として残せる。

会場で一つ選ぶならTRPGが向く。PCが別案を出した瞬間とGMの応答が見え、観客も同じ場面で自分の一手を出せる。デモでは作者が約束を一行読み、観客が最終手を選び、その後で模擬卓の結末と講評を開く。人間とモデルで判断が割れた場面が、次に作者が手を入れる候補になる。
