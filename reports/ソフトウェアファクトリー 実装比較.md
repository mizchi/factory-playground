# 作業の停止を見つけ、成果物の合格を確かめる

「テストが通った」と表示したエージェントが入力待ちに戻った。このとき、**作業者が応答を終えたこと**と、**要求どおりの成果物ができたこと**は、それぞれ何を見ればわかるだろう。laiso/agent-sessions は、すでに動いている作業者を見つけ、状態を読み、必要なら一度だけ促す監督の実装を示す。addyosmani/factory は、一件の要求に完了条件を付け、別の検証者が変更とテストを調べ、レビューに出せるかを判定する工程を示す。11月26日のハッカソンの例で言えば、前者を読むとハートビートの再開判断が、後者を読むと生成・検査・修正を繰り返すループの合格判断が具体的になる。対象は11月25日に取得した agent-sessions `10c08c2` と factory `8af1165`。[開催要項](https://software-factoriy.connpass.com/event/413858/)・[監督の判断表](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/skills/agent-sessions-supervisor/SKILL.md#L29-L51)・[検証者の手順](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/.claude/agents/factory-verifier.md#L16-L61)

## agent-sessions は送信後に同じ相手をもう一度読む

**端末の時計は進んでも、仕事が進んだとは限らない。** Herdrはスナップショットの状態を取り、tmuxは画面とフォーカスから状態を推定する。端末の読み取り時刻は毎回変わるため、監督者は同じペインの本文を比較する。実測では、フォーカスを外した模擬Codexに `Tests passed` と空の入力欄がある画面を与えると、一覧は `status=done`、読み取りは `structured=false` の端末本文を返した。この時点で得た証拠は「こう表示された」まで。実際に何をテストしたかは、成果物の側で調べる必要がある。[状態推定](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/src/agent_sessions/observe.py#L48-L85)・[画面のテスト例](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/tests/test_collection_regressions.py#L250-L261)・[本文の比較手順](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/skills/agent-sessions-supervisor/SKILL.md#L29-L49)

**通信が怪しいときは、再送の前に再読する。** tmuxでは、同じペイン番号が再利用されうるため、サーバーのPID・起動時刻とペインのPIDも照合する。貼り付け前の画面が取れなければ送信を中止する。貼り付け後は読み取りだけを繰り返す。テストでは、Enterに成功応答が返っても表示が下書きのままなら未確認の終了コード6になり、再送は0回だった。入力の二重確定が次の仕事まで起動しうる端末で借りたい技法だ。[宛先の同一性](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/src/agent_sessions/send.py#L32-L47)・[読み取りの再試行](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/src/agent_sessions/observe.py#L9-L33)・[成功応答だけが返るテスト](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/tests/test_delivery_regressions.py#L164-L174)

**独立した評価者に何を見せるかも設計する。** 同梱の `blind-test-coder` は、別ブランチで既存テストを読む前に取り除き、仕様書・`--help`・CLIの実行結果から別のテスト群を書かせる。仕様の解釈が割れた箇所は不具合と分けて報告する。別の `review-fix-loop` は査読者を交代させ、「異なる査読者が2回連続で重大な指摘ゼロ」を停止条件の例にする。どちらも担当者への指示であり、独立性は担当者が指示を守ることに依存する。[独立テスト担当の手順](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/skills/blind-test-coder/SKILL.md#L7-L40)・[交代レビューの終了条件](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/skills/review-fix-loop/SKILL.md#L14-L45)

## factory は一件の要求と検査条件を一緒に運ぶ

たとえば「この入力に対するCLIの出力を直してほしい」というissueを流す。まずトリアージ担当が、人が先に書いた `CHARTER.md` の自動化範囲に入るかを判断する。曖昧な要求には `needs-info`、設計判断が要るものには `ready-to-spec` を付ける。自動化できて期待する出力も確定していれば、`ready-to-implement` とし、`factory-handoff:v1` コメントに完了条件 `done_when`、変更予定ファイル、必要な検査レベルを残す。実装者が一件を取得し、実装とテストをコミットする。検証者が要求を満たすと判定したらPRを開き、最終マージは人が担う。Claude CodeとCodexは共通の工程を読み、Codex側のスキルは同じ手順を参照する薄いアダプターになっている。[分類](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/.claude/skills/factory-triage/SKILL.md#L42-L56)・[引き継ぎ](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/docs/factory/CONTRACT.md#L35-L81)・[PR前の検証](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/.claude/skills/factory-implement/SKILL.md#L93-L115)・[マージの担当](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/.claude/skills/factory-verify/SKILL.md#L58-L69)・[Codex側](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/template/.agents/skills/factory-implement/SKILL.md#L6-L11)

## 当日は二つの故障を実演できる

それぞれのリポジトリの上記コミットで、ルートから以下を実行する。最初のテストは「送ったつもりでも入力欄に残った」という故障を再現する。二番目はテストだけを残して修正を巻き戻す。Bashの `-x` を付けると、最終行の `proof: ok` に至る二つの判定を途中で読める。どちらもローカルのテスト用データで再現できる。[送達テスト](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/tests/test_delivery_regressions.py#L164-L174)・[修正巻き戻しテスト](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/tests/test-proof.sh#L12-L37)

```sh
# laiso/agent-sessions
python3 -m unittest -v tests.test_delivery_regressions.DeliveryTests.test_enter_ack_without_submission_is_unconfirmed

# addyosmani/factory
bash -x tests/test-proof.sh
```

**検証範囲。** agent-sessionsの単体テストはLinux/arm64・Python 3.14.10で93件すべて成功した。同じ版をPython 3.11.2のLinuxで実行した結果は92/93（Herdrの引数テストで1失敗）、Python 3.11.14のmacOSでは79/93（11失敗・3エラー）だった。macOSの複数のOrcaテストではテスト用環境からBashを見つけられなかった。factoryでは同梱の `test-claim.sh`、`test-gates.sh`、`test-proof.sh` が成功した。ここで測ったのは隔離した各部品の振る舞いで、ライブの作業者やGitHub上のissueからPRまでの完走率・時間・費用は未測定。[agent-sessionsのテスト環境](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/tests/helpers.py#L123-L143)・[Herdrの試験条件](https://github.com/laiso/agent-sessions/blob/10c08c25bde8230af2823836e4b2e060e939e042/tests/test_delivery_regressions.py#L60-L77)・[factoryの競合テスト](https://github.com/addyosmani/factory/blob/8af116567166a0a16588b7ab1b9934ece0b775bc/tests/test-claim.sh#L4-L34)

## 生成中に人を呼びたくなったら、何を記録して終えるか

イベント向けの応用として、発表する生成物を「受け入れ検査を通過した候補」と定義し、開始前にサンプル入出力、再試行の上限、終了条件を与えておく。実行中に進捗が止まったら、監督役は同じ宛先を再観測する。検査で落ちたら、その入力・期待値・実測値を次の自動修正に渡す。権限や仕様の判断が必要になった回は、その要求と観測を残して終了する。実行後に人が入力や検査を直して再生成でき、選んだ成果物には手を加えずに済む。発表では、**どの入力で、何を失敗と判定し、次の試行に何を渡したか**を一件たどれば、未完成の回もファクトリーの設計として説明できる。[開催要項と発表内容](https://software-factoriy.connpass.com/event/413858/)
